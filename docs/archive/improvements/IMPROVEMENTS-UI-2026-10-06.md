# Eternal Rest — UI Improvements

**Analysis date:** 2026-10-05
**Completed and archived:** 2026-10-06
**Status:** Completed — all five selected improvements (IMP-UI-01 to IMP-UI-05) are implemented; this document is an archived historical record
**Project type:** Polish-language static multi-page website (nine root HTML pages, plain CSS with custom properties, Vanilla JavaScript ES module, Vite 5 MPA build)
**Analysis mode:** Evidence-based UI improvement review
**Focus:** Project-wide UI

## Overview

At the time of the analysis, the interface had a consistent token base in `css/tokens.css`, a restrained warm palette with light, dark and system themes, and a shared BEM vocabulary across all nine pages. The legal family (`css/pages/legal.css`) showed the most mature UI layer: measured text width, tokenized heading rhythm and explicit link states.

The review found that the six marketing pages had not caught up with that layer. Action styles were borrowed across blocks: the header CTA class served as the page-wide primary button, and the `badge` label was reused for links and toggle buttons. The pricing page had no multi-column layout. Display headings inherited the body line-height. The ARIA states maintained by `js/main.js` had no visual presentation. Surface and elevation tokens did not separate cards from alternate sections, and dark mode did not override the shadow tokens.

The review selected five improvements, IMP-UI-01 to IMP-UI-05, scoped to the existing tokens, breakpoints (480, 760, 1024 px) and `data-*` behavior contracts. All five were implemented on 2026-10-05 and 2026-10-06, each as a focused change, and none modified `js/main.js`. Defects observed during the analysis were deliberately kept outside the improvement scope and were not addressed by this cycle; they are listed under [Excluded defects](#excluded-defects).

### How to read this record

- **Original state** and **Original evidence** describe the repository as analyzed on 2026-10-05 (commit `7b844d7`). Their file and line references point to that revision and may no longer match the current source.
- **Planned improvement**, **Expected value** and **Acceptance criteria** record the scope agreed before implementation.
- **Implemented result** describes the delivered change. It was re-checked against the source by static inspection when this document was archived on 2026-10-06.
- **Verification** lists only the checks recorded when each item was completed. No lint, build or browser check was repeated for archiving.

## Completed improvements

### IMP-UI-01 — Separate a shared button component from the header CTA and the badge label

- **Status:** Completed (commit `f8430f5`)
- **Affected area:** Primary and secondary actions on the marketing pages; action styles in `css/components.css`.
- **Original state:** `site-header__cta`, an element of the header block, was the only primary-button style and was reused on five pages, including the form submit. `.badge` rendered static service tags, navigational links, pricing detail toggles and contact-method toggles with identical presentation. Only `.site-header__cta` defined a hover and focus treatment; badge links and badge buttons had no hover or active styling. As a result, "Zobacz szczegóły" on the home cards looked the same as the non-interactive "Oprawa muzyczna" tag on the services page.
- **Original evidence:** `css/components.css:77-95` (`.site-header__cta`), `css/components.css:220-229` (`.badge`); header CTA class used outside the header at `index.html:78`, `index.html:261`, `services.html:141`, `pricing.html:159`, `guide.html:162` and as the form submit at `contact.html:162`; `.badge` used as links at `index.html:79`, `index.html:148-158`, `contact.html:196`, as buttons at `pricing.html:92-142` and `contact.html:119-135`, and as static labels at `services.html:85-136` and `index.html:95`.
- **Planned improvement:** Introduce a page-level button block in `css/components.css` with primary and secondary variants built only from existing tokens (accent, surface-alt, pill radius, existing padding), with hover, focus-visible and active states. Migrate the non-header primary actions and every interactive badge use to it, and keep `.badge` for non-interactive labels only. The header CTA could adopt the primary variant or keep its class, with identical appearance. The change was limited to `css/components.css` and class attributes in `index.html`, `services.html`, `pricing.html`, `guide.html` and `contact.html`; `data-*` hooks, `aria-expanded`/`aria-pressed` handling, `tel:` links, labels and the global `:focus-visible` outline had to remain unchanged.
- **Expected value:** Actions are visually distinguishable from labels. Page CTAs no longer depend on a header element, so header changes do not ripple into page content. Action states have a single owner.
- **Acceptance criteria:** No element outside `.site-header` uses `site-header__cta`. No `a.badge` or `button.badge` remains. Interactive secondary actions share one variant with visible hover and active states in light and dark themes. Primary actions keep their original colors, pill shape and padding. Pricing toggles and contact-method buttons keep their existing ARIA behavior. `npm run lint` and `npm run build` succeed.
- **Impact:** High
- **Effort:** Medium
- **Implemented result:** `css/components.css` defines a `.button` block whose base rule owns the pill shape, padding, weight, the hover/focus-visible lift and an `:active` press state, with `.button--primary` (accent background and border, white text, as before) and `.button--secondary` (`--color-surface-alt` background, `--color-accent-soft` border, `--color-text` label, accent border on hover and an accent-soft tint on `:active`). The six non-header primary actions use `button button--primary`, and the ten formerly badge-styled controls (three home card links, two `tel:` links, three pricing detail toggles and two contact-method toggles) use `button button--secondary`. The header CTA keeps its unchanged `.site-header__cta` rules, and the class appears only inside the header on all nine pages. `.badge` remains on non-interactive labels only: the "Tarnów i okolice" label on the home page, the service tags in `services.html` and the header phone label on all nine pages, which the original evidence did not list. `data-*` hooks, ARIA attributes, `tel:` links, labels and `js/main.js` are unchanged.
- **Verification:** `npm run lint` and `npm run build` passed at completion.
- **Known limitations:** The contact-method `aria-pressed` selected state is still not presented, and the dark-theme white-on-accent contrast defect now also applies to `.button--primary`; both are [excluded defects](#excluded-defects).

### IMP-UI-02 — Add a responsive comparison layout to the pricing packages

- **Status:** Completed (commit `63ae02a`)
- **Affected area:** `pricing.html` package list and filter.
- **Original state:** `.pricing` defined a gap but no columns at any breakpoint, so the three packages stacked vertically at every width. Because `.pricing__card` is a grid, the badge-styled details toggle stretched to the full card width. The filter field also spanned the whole container.
- **Original evidence:** `css/components.css:287-314` (`.pricing`, `.pricing__card`, `.pricing__details`), `pricing.html:78-151`, `js/main.js:216-240`, `css/layout.css:47-49` and `css/layout.css:61-68` (existing `grid--three` breakpoint pattern). Runtime at a 1280 px viewport: `.pricing` computed to a single `1120px` track, each card measured 1120 × 237 px, the details toggle stretched to 1070 px and the filter select to 1120 px.
- **Planned improvement:** Give `.pricing` a mobile-first column layout using the existing breakpoints, so the three packages sit side by side on wide viewports. Align cards so that expanding one card's details does not resize its neighbors. Size the details toggle to its content and constrain the filter control to a readable width. When the filter leaves a single card visible, the card should keep its column width instead of spanning the container. The change was limited to `.pricing` rules in `css/components.css`, plus a wrapper class on the filter field in `pricing.html` only if needed, and had to preserve `data-pricing-card`, `data-category`, the `is-hidden` filtering, `aria-controls` IDs, `hidden` toggling and all copy.
- **Expected value:** Price ranges and package descriptions can be compared at a glance. The page aligns with the three-column card grids used elsewhere, and line length inside cards becomes shorter.
- **Acceptance criteria:** All three cards share one row at the chosen desktop breakpoint, and the layout is single-column below 480 px. Expanding one card's details changes only that card's height. Details toggles are no wider than their label plus padding. The filter select does not span the full container at 760 px and above. Filtering to one category shows one card at column width. No horizontal overflow appears at 375 px.
- **Impact:** High
- **Effort:** Small
- **Implemented result:** `.pricing` stays single-column by default, switches to `repeat(3, minmax(0, 1fr))` from the existing 760 px breakpoint and uses `align-items: start`, so expanding one card's details does not stretch its neighbors and a single filtered package keeps its column width. `.pricing__card > .button` uses `justify-self: start`, so the detail toggles, `.button--secondary` since IMP-UI-01, size to their labels. The filter field has a `pricing-filter` class in `pricing.html`, constrained to `max-width: 20rem` from 760 px. Filtering, disclosure, ARIA attributes and copy are unchanged.
- **Verification:** `npm run lint`, `npm run build` and a focused browser check at 375 px and 1280 px passed at completion.
- **Known limitations:** The remaining horizontal page overflow at 375 px comes from the excluded [shared-header defect](#excluded-defects), not from the pricing layout.

### IMP-UI-03 — Establish a tokenized, responsive heading scale for the marketing pages

- **Status:** Completed (commit `eaa4a0b`)
- **Affected area:** Hero, section, card, service and footer headings on the six marketing pages; typography tokens.
- **Original state:** Serif display headings on the marketing pages inherited the body line-height of 1.6. `.section__title` had one size for page `h1` elements and for the home hero card `h2`, with no responsive step. The hero's largest size was a literal value outside the token scale. The legal pages solved heading rhythm locally, which left two independent heading systems.
- **Original evidence:** `css/tokens.css:18-26` (size tokens only, no line-height tokens), `css/base.css:17` (body `line-height: 1.6`), `css/layout.css:27-31` (`.section__title`), `css/components.css:175-179` and `css/components.css:471-475` (`.hero__title`, with a `3.4rem` literal at 1024 px), `css/components.css:211-214` (`.card__title`), `css/pages/services.css:13-17`, `css/pages/legal.css:40-52` and `css/pages/legal.css:144-155` (legal headings set their own line-height and `text-wrap: balance`). Runtime: the home `h1` rendered at 54.4 px with an 87.04 px line-height at 1280 px and at 45.6 px at 375 px; `.section__title` rendered at 36 px at both widths.
- **Planned improvement:** Add heading line-height tokens and a display-size token in `css/tokens.css`. Define small-screen and 760 px+ sizes for `.hero__title` and `.section__title` using the existing breakpoints. Apply the heading line-height and balanced wrapping to the shared serif heading classes, and let `css/pages/legal.css` consume the same tokens without visual change. The change was limited to `css/tokens.css`, `css/layout.css`, `css/components.css`, `css/pages/services.css` and token adoption in `css/pages/legal.css`, with no HTML changes, and had to preserve font families, weights, colors and heading levels.
- **Expected value:** Multi-line titles become tighter and more cohesive, use less vertical space on small screens, and follow one heading system across marketing and legal pages.
- **Acceptance criteria:** Heading rules (`.hero__title`, `.section__title`, `.card__title`, `.services-list__title`, `.footer__title`, `.site-header__brand-title`, legal headings) take sizes and line-heights from tokens rather than literals or the inherited body value. `.hero__title` and `.section__title` are smaller below 760 px than at 760 px and above. Legal heading sizes are visually unchanged. No horizontal overflow occurs at 320 px or 375 px.
- **Impact:** Medium
- **Effort:** Medium
- **Implemented result:** `css/tokens.css` defines `--line-height-display` (1.2), `--line-height-heading` (1.4) and `--font-size-5xl` (3.4rem, replacing the hero literal). `.hero__title` steps from `--font-size-3xl` to `--font-size-4xl` at 760 px and `--font-size-5xl` at 1024 px, and `.section__title` steps from `--font-size-2xl` to `--font-size-3xl` at 760 px; both use the display line-height and `text-wrap: balance`. `.card__title`, `.services-list__title`, `.footer__title` and `.site-header__brand-title` use the heading line-height. In `css/pages/legal.css`, the shared legal heading rule owns the heading line-height and `.legal-hero__title` uses the display token, replacing the former local `1.2` and `1.4` literals with the same values, so legal heading sizes and rhythm are unchanged. No HTML changed.
- **Verification:** `npm run lint`, `npm run build` and a focused browser check at 320, 375 and 1280 px passed at completion.
- **Known limitations:** The remaining horizontal page overflow at 320 and 375 px comes from the excluded [shared-header defect](#excluded-defects).

### IMP-UI-04 — Present the disclosure and validation states that `js/main.js` already maintains

- **Status:** Completed (commit `0c8bbf3`)
- **Affected area:** FAQ accordions (`index.html`, `guide.html`), pricing detail toggles, contact form fields.
- **Original state:** Open and closed accordion items looked identical apart from the revealed panel. Triggers had no indicator, no hover state and no emphasis over body text. Invalid form controls kept their default border, and the only cue was 13 px error text below the field.
- **Original evidence:** `js/main.js:202-214` (accordion `aria-expanded`), `js/main.js:228-240` (details `aria-expanded`), `js/main.js:264-279` (`aria-invalid`); `css/components.css:257-285` (accordion), `css/components.css:326-343` (form controls and errors); no rule in `css/` targeted `aria-expanded` or `aria-invalid`; markup at `index.html:230-259`, `guide.html:77-136`, `contact.html:79-175`. Runtime: accordion triggers rendered at font-weight 400 on the same surface as their panels; after an empty submission, `#name` carried `aria-invalid="true"` while its border stayed at the default `--color-border` value.
- **Planned improvement:** Add CSS-only presentation keyed to the attributes the script already writes. Accordion triggers get a decorative expand/collapse indicator that changes with `[aria-expanded="true"]`, a heavier question weight and a hover/focus-visible surface tint; pricing detail toggles may reuse the same indicator. Controls marked `[aria-invalid="true"]` get an error-colored border using `--color-error`. The change was limited to `css/components.css`. Indicators had to be decorative (pseudo-elements or `aria-hidden`) so accessible names stay unchanged, and transitions had to use the existing tokens so reduced-motion handling still applies. `js/main.js`, the `hidden` attribute usage and the error message wiring had to stay unchanged. The contact-method `aria-pressed` presentation was a separate [excluded defect](#excluded-defects) and outside this item.
- **Expected value:** Users can see the open, closed and invalid states without relying on panel content or small text. The presentation stays synchronized because it derives from the existing ARIA state.
- **Acceptance criteria:** Each accordion trigger shows an indicator that differs between collapsed and expanded states in light and dark themes, and has a visible hover state. After an empty submission, every invalid control shows an error-colored border, which disappears once the field is filled and the form is resubmitted. Trigger accessible names are unchanged, and `js/main.js` is not modified.
- **Impact:** Medium
- **Effort:** Small
- **Implemented result:** `.accordion__button` uses font-weight 600 and, on hover and focus-visible, a surface tint mixing `--color-accent-soft` into `--color-surface`, with a `--transition-fast` background transition. An empty `::after` pseudo-element on `.accordion__button` and on `.button[aria-expanded]` (the pricing detail toggles) draws a decorative accent chevron that points down when collapsed and rotates to point up when `[aria-expanded="true"]`, using a `--transition-fast` transform transition. `.form__input`, `.form__select` and `.form__textarea` marked `[aria-invalid="true"]` use a `--color-error` border; because `js/main.js` removes the attribute when a field passes revalidation, the border returns to the default after a successful resubmission. HTML, `js/main.js`, `hidden` handling, accessible names and ARIA behavior are unchanged.
- **Verification:** `npm run lint`, `npm run build` and a focused browser check of the disclosure and validation states in light and dark themes and at 375 px passed at completion.

### IMP-UI-05 — Make surface and elevation tokens separate content blocks from alternate sections in both themes

- **Status:** Completed (commit `a00f9d6`)
- **Affected area:** Cards, process steps, testimonials and service items, particularly inside `.section--alt`; theme tokens.
- **Original state:** Content blocks used the same surface color as `.section--alt` in both themes, so on alternate sections only a 1 px border separated them from the background. Dark mode did not override the shadow tokens, so they kept light-theme values. The dark-specific `--color-shadow` was defined three times but unused. Elevation varied by block type: `.card` and `.testimonial` used `--shadow-sm`, `.hero__card` used `--shadow-md`, and `.steps__item` and `.services-list__item` had none.
- **Original evidence:** `css/tokens.css:4` and `css/tokens.css:13` (`--color-surface`, `--color-shadow`), `css/tokens.css:43-45` (shadow tokens defined only in `:root`), `css/tokens.css:54-67` and `css/tokens.css:73-88` (dark overrides, including `--color-shadow`, which no rule consumed); `css/layout.css:10-12` (`.section--alt` uses `--color-surface`); `css/components.css:193-209`, `css/components.css:236-255`, `css/pages/services.css:6-11`; affected markup at `index.html:101-135`, `index.html:164-189`, `about.html:99-123`, `guide.html:140-160`. Runtime in system dark mode: `.section--alt` and `.card` both computed to `rgb(31, 27, 24)`, the card shadow resolved to the light-theme `rgba(42, 36, 32, 0.12)` value, and `.steps__item` had no shadow.
- **Planned improvement:** Make the elevation tokens theme-aware by redefining the shadow tokens in both dark-theme blocks, replacing or consuming the unused `--color-shadow`. Define the surface relationship for content blocks placed inside `.section--alt` through a token or a section-scoped rule, and align elevation across the four block types according to one documented choice. The change was limited to `css/tokens.css` (both dark blocks, which duplicated each other), `css/layout.css` and/or `css/components.css`, with no HTML or JavaScript changes; the existing palette values and the explicit/system theme mechanism had to stay unchanged.
- **Expected value:** Grouping and hierarchy on alternating sections stay legible in light, dark and system-dark modes, and an unused token is removed from the theme layer.
- **Acceptance criteria:** On every `.section--alt`, card, step and testimonial backgrounds differ from the section background in light, explicit dark and system-dark modes. Shadow tokens resolve to theme-specific values in dark mode. `--color-shadow` is either used or removed with no remaining references. Light-theme blocks on default sections look unchanged.
- **Impact:** Medium
- **Effort:** Small
- **Implemented result:** The explicit-dark (`html[data-theme="dark"]`) and system-dark (`html:not([data-theme])` under `prefers-color-scheme: dark`) blocks in `css/tokens.css` define matching `--shadow-sm`, `--shadow-md` and `--shadow-lg` overrides that keep the light-theme geometry and use a near-black shadow color whose opacity rises with elevation (0.45, 0.5, 0.6). `--color-shadow` was removed from all three theme blocks and has no remaining references. Section-scoped rules in `css/components.css` (`.card`, `.steps__item`, `.testimonial`) and `css/pages/services.css` (`.services-list__item`) place these blocks on `--color-bg` with `--shadow-sm` inside `.section--alt`. The documented elevation choice is therefore: inside alternate sections all four block types share `--shadow-sm`, while on default sections the original per-block elevation, including `.hero__card` with `--shadow-md`, is unchanged. Palette values, HTML and JavaScript are unchanged.
- **Verification:** `npm run lint`, `npm run build` and a focused explicit light, explicit dark and system-dark browser check of the home, about and guide pages passed at completion. No testimonial or service list sat inside an alternate section at that time, so those two selectors were confirmed on temporary in-browser probe elements.
- **Known limitations:** The explicit-dark and system-dark blocks still duplicate their token values; consolidating them was not part of this item.

## Selection summary

The five items were selected because they applied across several pages, reused existing tokens and breakpoints, and could each be delivered as a focused task without changing behavior contracts. IMP-UI-01 and IMP-UI-02 had the most visible effect on the marketing pages, IMP-UI-03 and IMP-UI-05 strengthened the shared token layer, and IMP-UI-04 was a small, CSS-only change. All five are complete. Each was delivered in its own commit, and none changed `js/main.js`, the `data-*` and ARIA contracts in the HTML or the theme mechanism.

Order and dependencies: IMP-UI-01, IMP-UI-02 and IMP-UI-04 all touched the pricing detail toggles, so IMP-UI-01 was implemented first to avoid restyling them twice. IMP-UI-02 then sized the new `.button--secondary` toggles inside the pricing cards, and IMP-UI-04 added its disclosure indicator to them through `.button[aria-expanded]`. IMP-UI-03 and IMP-UI-05 were independent of each other and of the rest. The items were implemented in numerical order.

## Excluded defects

The following defects were observed during the analysis and deliberately excluded from the improvement proposals because they belong in a defect audit. They are not part of IMP-UI-01 to IMP-UI-05 and were not resolved by this cycle. The measurements come from the 2026-10-05 analysis; at archiving, only the source was re-checked.

- **Shared header on the six marketing pages:** at 375 px the closed menu panel widened the layout to 750 px. When opened, the panel measured 375 × 112 px, the size of the header box, instead of covering the viewport, so the menu items overlaid page content. At 1280 px the menu toggle remained visible and navigation labels and the CTA wrapped to two lines. The legal pages avoid this through scoped rules in `css/pages/legal.css` (lines 6-20 and 268-303 at analysis). The completion checks for IMP-UI-02 and IMP-UI-03 attributed the remaining 320 and 375 px page overflow to this defect.
- **Contact-method toggles:** `aria-pressed="true"` and `aria-pressed="false"` rendered with identical computed styles. IMP-UI-01 moved both toggles to `.button--secondary` without adding a selected state, and no rule in `css/` targets `aria-pressed`.
- **White text on the dark-theme accent:** white on `#c58a52` computes to a 2.94:1 contrast ratio (4.67:1 on the light-theme `#9a6a3a`). At analysis this affected `.site-header__cta`, `.back-to-top` and `.skip-link`; since IMP-UI-01 it also affects `.button--primary`.

A current-page indicator for the primary navigation was not proposed because the shared header needed to be corrected first.

## Analysis limitations

These limitations apply to the original 2026-10-05 analysis. The checks made when each item was completed are listed under its **Verification** entry.

- Rendering was checked by serving the source tree from a temporary local static server and inspecting it in a Chromium-based browser at 375 × 812 and 1280 × 900, in emulated light and dark schemes. This was not the Vite dev server or production build (no Autoprefixer), and other browsers and intermediate widths were not inspected.
- Manrope and Playfair Display were named in the font stacks but not loaded, so the wrapping and heading measurements reflect the fallback fonts in the inspection environment.
- The contrast ratios were calculated from the declared token values, not measured on rendered pixels.
- No `PLAN.md`, audit or review file existed at the time. Overlap with planned or completed work was checked only against `docs/CONTEXT-PROJECT.md`, `docs/CHANGELOG.md` and `README.md`.
