# Eternal Rest — Workflow Improvements

**Analysis date:** 2026-10-06
**Completed and archived:** 2026-10-08
**Status:** Completed and archived — all five selected improvements (IMP-WORKFLOW-01 to IMP-WORKFLOW-05) are closed; this document is an archived historical record
**Project type:** Polish-language static multi-page website (nine root HTML pages, plain CSS with custom properties, Vanilla JavaScript ES module, Vite 5 MPA build, npm tooling)
**Analysis mode:** Evidence-based workflow improvement review
**Focus:** Project-wide workflow

## Overview

At the time of the analysis, the development workflow was small and mostly well documented. Six npm scripts in `package.json` covered development, build, preview, lint, formatting and image conversion. `vite.config.js` was the only build configuration, and `dist/` was generated and ignored. `AGENTS.md` (imported by `CLAUDE.md`) held the shared contributor contract, a separate project context document in `docs/` held stable technical contracts, and `docs/CHANGELOG.md` had an explicit entry policy. Improvement reports had an archive directory and one completed UI cycle.

The review found gaps in the steps around that core. Manual deployment and the improvement-report status format were referenced but not written down. The supported Node.js version was only implicit. The page inventory was maintained by hand in `vite.config.js` and in page-count wording across README and the context document. The formatting command could only rewrite the whole repository.

The review selected five improvements, IMP-WORKFLOW-01 to IMP-WORKFLOW-05, and all five were closed between 2026-10-06 and 2026-10-08. On 2026-10-07, during the cycle, the owner adopted a simplified documentation model: the context document was removed, `AGENTS.md` was reduced to stable guardrails, and `README.md` became the primary project reference. As a result, IMP-WORKFLOW-01 was implemented and later superseded, and IMP-WORKFLOW-02 was resolved through that model instead of its original release-procedure proposal. IMP-WORKFLOW-03 and IMP-WORKFLOW-04 were implemented as planned, and IMP-WORKFLOW-05 was implemented without a baseline format. One documentation defect observed during the analysis remained open at archiving; see [Excluded observations](#excluded-observations).

At archiving, project documentation consists of `README.md` (project overview, architecture, setup, development and implementation limitations), `AGENTS.md` (stable project guardrails, imported by `CLAUDE.md`), `docs/CHANGELOG.md` (significant completed changes) and `docs/archive/` (completed historical records).

## Completed improvements

### IMP-WORKFLOW-01 — Define the improvement-report lifecycle in the project contract

- **Status:** Completed (commit `b7c8e4f`); superseded on 2026-10-07 by the simplified documentation model (commit `4f74c29`)
- **Affected workflow:** Improvement-report maintenance: recording item completion during implementation and archiving a completed report.
- **Original state:** The repository recorded only where completed reviews go. The status-line format, the point at which a report is archived, the archive filename pattern (the single example was `IMPROVEMENTS-UI-<YYYY-MM-DD>.md`) and the structure of an archived record had to be inferred from one completed cycle. During that cycle the status format changed once and one item ended up with two status lines. Archiving then required restructuring the full report.
- **Original evidence:** `AGENTS.md:20` (names only the archive directory `docs/archive/improvements/`); `AGENTS.md:100` ("Use the project's established concise completion format"; no repository file defined that format); `docs/CHANGELOG.md:24` (status updates and archiving are not changelog entries); the pre-archive report (`git show 200ef33^:IMPROVEMENTS-UI.md`, lines 18 and 28) gave IMP-UI-01 two `**Status:**` lines in different forms (`Completed — …` and `Implemented. …`); commit `7d10c0a` ("Standardize improvement status and changelog policy") changed the status wording during the cycle; `docs/archive/improvements/IMPROVEMENTS-UI-2026-10-06.md:1-24` and commit `200ef33` show that archiving rewrote the whole report with new header fields, a "How to read this record" section and renamed item fields (Original state, Original evidence, Planned improvement, Implemented result, Verification, Known limitations).
- **Planned improvement:** Add a short improvement-report lifecycle rule next to the existing rules in `AGENTS.md`, consolidating lines 20 and 100 where needed. The rule would cover the active report location and name (`IMPROVEMENTS-<AREA>.md` in the root), one per-item status format (outcome, commit reference, checks actually run), when a report is archived, the archive filename pattern and the minimum archived-record fields, with the UI archive as the reference example instead of a new template file. If the status format came from a global KP_Code standard kept outside the repository, the local rule would reference that standard and record only project-specific choices. `CLAUDE.md` would stay import-only, and the rule would not be repeated in README or other documentation files. The archived UI report, the changelog entry policy, scripts and tooling were out of scope.
- **Expected value:** Each new cycle records completion in one form from the first completed item. Archiving needs less restructuring because the archived fields are defined in advance. The instruction at `AGENTS.md:100` points to a format that can actually be found.
- **Acceptance criteria:** `AGENTS.md` states the active report location and naming, a single status-line format that includes the commit and the verification actually run, the archive trigger, and an archive filename pattern that matches `docs/archive/improvements/IMPROVEMENTS-UI-2026-10-06.md`. The completion format referenced at `AGENTS.md:100` is defined, or explicitly referenced, in the repository. The rule exists in exactly one project file.
- **Impact:** Medium
- **Effort:** Small
- **Implemented result:** Commit `b7c8e4f` added a "Working-document lifecycle" section to `AGENTS.md`, pointed the reading-list entry at line 20 to it and removed the instruction at line 100. The section kept active plans, audits and improvement reports (`IMPROVEMENTS-<AREA>.md`) at the repository root; required exactly one status line per completed item in the form `**Status:** Completed — <delivered outcome>. <verification actually performed>.`; allowed archiving only when a work cycle is deliberately closed; defined category archives under `docs/archive/` and the `IMPROVEMENTS-<AREA>-YYYY-MM-DD.md` filename pattern; and listed the context an archived record should keep, with the UI archive as a reference example rather than a mandatory template. Commit references were made optional instead of part of the status format, which departed from the acceptance criterion that the status line include the commit. A Documentation entry in `docs/CHANGELOG.md` recorded the change. On 2026-10-07, commit `4f74c29` reduced `AGENTS.md` to stable guardrails and removed the lifecycle section. At archiving, no current project file defines an active-report location, status format, archive trigger or archive filename pattern; the changelog entry remains as a historical record, followed by the entry for the simplified documentation model.
- **Verification:** At completion, a static review confirmed that the rule existed in exactly one project file and added no Git or execution-workflow requirement. No lint, build or browser check was run because application behavior was unchanged. The supersession was confirmed for archiving by static inspection of commit `4f74c29` and the current `AGENTS.md`.
- **Known limitations:** The repository no longer defines an improvement-report lifecycle. This record follows the structure of the archived UI report and the archive filename approved by the owner for this cycle; neither is a current project rule.

### IMP-WORKFLOW-02 — Align project documentation with the simplified documentation model

- **Status:** Completed through an alternative accepted decision (commits `a3f3b01`, `4f74c29`, `a1b00e6` and `795cdeb`); the original release-documentation proposal was not adopted
- **Affected workflow:** Project documentation ownership, including how the public live demo is described. The original proposal targeted deployment preparation and release recording.
- **Original state:** The repository defined the artifact (`npm run build` → `dist/`) and a local inspection command (`npm run preview`). `AGENTS.md` referred to a manual deployment workflow that no file described: there were no pre-publish checks, no documented route for `dist/` to reach the host, and no record of which revision was published. Every change since the first commit remained under `[Unreleased]`, the package version had not changed, and there were no tags. As a result, the repository could not identify the live revision, and README had to disclaim the preview URL.
- **Original evidence:** `AGENTS.md:61` (contributors must follow "the project's manual deployment workflow"); `README.md:11-13` and `README.md:143-145` (preview URL whose correspondence with the repository revision "has not been confirmed"); `README.md:105` and `README.md:237` (`dist/` is excluded from Git, and the repository contains no hosting or automated deployment configuration); `docs/CHANGELOG.md:7` (every entry sits under `[Unreleased]`); `package.json:3` (`"version": "1.0.0"`); the repository had no Git tags.
- **Planned improvement (original proposal, not adopted):** Under the original title "Document the manual release procedure and make the deployed revision traceable", add one short manual release procedure to the "Deployment" section of the context document. The procedure would cover a clean install (`npm ci`), `npm run lint`, `npm run build`, a local check with `npm run preview`, the owner's actual method of publishing `dist/`, and a recording step that ties the published commit to a dated changelog release heading, optionally with an owner-created Git tag. It would also state whether `package.json` `version` follows release headings or stays fixed. README would link to the procedure instead of restating it, and `docs/CHANGELOG.md` would gain a release-heading convention. No hosting configuration, CI workflow, deployment script or version-bump tooling was planned.
- **Accepted decision:** The owner decided that project documentation describes the project itself, not the owner's delivery process. Instead of a release procedure, the context document was removed and `AGENTS.md`, imported by `CLAUDE.md`, was reduced to stable guardrails, so the manual-deployment reference no longer exists. `README.md` owns the project overview, local setup, build and preview instructions, implementation limitations and one owner-confirmed live-demo link per language. No release procedure, deployed-revision tracking, Git tags or version-bump rules are documented.
- **Expected value:** Under the accepted decision, each documentation file has one clear role, README presents the live demo without a disclaimer, and project documentation does not prescribe a personal delivery workflow that could drift from the owner's actual practice. The original proposal instead aimed to give `AGENTS.md:61` a concrete referent and to relate the live demo to a specific commit and changelog section.
- **Acceptance criteria:** The original criteria, which required one file to own the release procedure and `AGENTS.md:61` to refer to an existing workflow, were replaced by the following: the context document does not exist and no current project document relies on it as a source. Both README languages state equivalent facts, use only commands defined in `package.json` and paths that exist, and link the owner-confirmed live demo once without claiming a deployed revision. README, `AGENTS.md` and `CLAUDE.md` contain no deployment, release, Git or agent-execution procedure. No deployment, CI or hosting file is added.
- **Impact:** High
- **Effort:** Small
- **Implemented result:** On 2026-10-07, commit `a3f3b01` removed the context document. Commit `4f74c29` reduced `AGENTS.md` to stable guardrails, removing, among other content, its reading-list entry for the context document, the manual-deployment instruction (formerly `AGENTS.md:61`) and the lifecycle added under IMP-WORKFLOW-01. Commit `a1b00e6` reduced `CLAUDE.md` to the `@AGENTS.md` import and a note that no Claude-specific rules are defined. Commit `795cdeb` replaced the README preview disclaimer in both languages with the public demo link, moved the changelog Entry policy before `[Unreleased]` so that the unreleased subsections belong to it, and added a Documentation entry for the simplified model. The README structure trees were kept limited to the application codebase. `package.json` `version` remains `1.0.0`, the repository has no Git tags, and no release procedure or deployment, CI or hosting file was added.
- **Verification:** At completion, a static review verified README commands, paths and PL/EN consistency against the repository; no runtime checks or deployment were performed. At archiving, static inspection confirmed that the context document does not exist and that `README.md`, `AGENTS.md`, `CLAUDE.md` and `docs/CHANGELOG.md` do not present it as a current or required document.
- **Known limitations:** The repository does not record which revision is deployed at the live-demo URL, and no inspection of the live site is recorded for this cycle; both follow from the accepted decision. The `.gitignore` comment that still listed the context document was outside this item and remained an [open observation](#excluded-observations) at archiving.

### IMP-WORKFLOW-03 — Declare the supported Node.js and npm versions

- **Status:** Completed (commit `aa7281c`)
- **Affected workflow:** Development setup and reproducible dependency installation.
- **Original state:** The setup instructions required Node.js, npm and `npm ci`, but the supported runtime existed only in the engine ranges of locked third-party packages. The required dependencies set a floor of Node `^18.17.0 || ^20.3.0 || >=21.0.0` and npm `>=8`. On Linux x64, one optional rollup dependency required Node `^22.20 || ^24.12 || >=25`. Both constraints could only be found by reading the lockfile, and the second one depended on the platform. npm does not enforce engine ranges by default, so an unsuitable runtime showed up only as engine warnings for individual packages or as a later tool failure.
- **Original evidence:** `package.json:1-25` (no `engines` field); the root had no `.nvmrc`, `.node-version` or `.npmrc`; `README.md:80` and `README.md:212` ("Node.js and npm are required", without versions), and no other project document stated a version; locked dependency constraints: `package-lock.json:2758` (sharp 0.33.5, Node `^18.17.0 || ^20.3.0 || >=21.0.0`), `package-lock.json:2977` (vite 5.4.21, Node `^18.0.0 || >=20.0.0`), `package-lock.json:2675-2676` (rollup 4.64.0, Node `>=18.0.0`, npm `>=8.0.0`); `package-lock.json:918` (`@napi-rs/lzma-linux-x64-gnu` 1.5.1, an optional Linux x64 dependency of rollup, Node `^22.20 || ^24.12 || >=25`); `package-lock.json:4` (`lockfileVersion: 3`).
- **Planned improvement:** Record the supported Node.js and npm range once, in `package.json` `engines`. Choose a range that falls within the locked dependency constraints, accounts for the optional platform-specific constraint above, and includes the version the owner actually uses. Update the matching root-package entry in `package-lock.json` through npm's own tooling with no change to resolved dependency versions, and reference the range in both README installation sections. No dependency upgrades, no `engine-strict` enforcement and no required version-manager file.
- **Expected value:** A fresh clone states its expected runtime before `npm ci`. Mismatches are reported against the project's own declaration, not only against transitive packages. The README requirement becomes specific and verifiable.
- **Acceptance criteria:** `package.json` declares an `engines` range that falls within the required-dependency constraints above. The range either falls within the optional Linux x64 constraint or the documentation explains why it does not. README (PL and EN) states the same range. `npm ci` on a Node.js version inside the range reports no engine warnings for required packages. The diff of `package-lock.json` contains no resolved-version changes.
- **Impact:** Medium
- **Effort:** Small
- **Implemented result:** `package.json` declares `"engines": { "node": ">=22.20.0 <23", "npm": ">=10" }`. The Node.js range falls within the required-dependency constraints and within the optional Linux x64 constraint (`^22.20`), so no explanatory note was needed. The root-package entry in `package-lock.json` gained the same `engines` block through npm; the lockfile diff in `aa7281c` adds only that block. README states "Node.js 22.20+ z linii 22.x oraz npm 10 lub nowszy" (PL) and "Node.js 22.20+ within the 22.x line and npm 10 or newer" (EN). No `engine-strict` setting or version-manager file was added. A Build and Tooling entry in `docs/CHANGELOG.md` records the change.
- **Verification:** At completion, `npm ci`, lint and build completed successfully without engine warnings on Node.js 22.23.2 and npm 10.9.8, the owner's local environment.
- **Known limitations:** npm does not enforce `engines` without `engine-strict`, so an out-of-range runtime still produces only warnings. Only Node.js 22.23.2 was verified, and Node.js release lines other than 22.x are outside the declared range.

### IMP-WORKFLOW-04 — Make the root HTML pages the single source of the page inventory

- **Status:** Completed (commit `ee06795`)
- **Affected workflow:** Adding, renaming or removing a page (build entries and documentation synchronization).
- **Original state:** Each new page had to be registered by hand in `vite.config.js`, and the total page count was repeated in sentences across both README languages and the context document. Vite built only the listed inputs, so a page that was not registered was left out of `dist/` and the build did not report the omission.
- **Original evidence:** `vite.config.js:12-22` (nine hand-written `rollupOptions.input` entries); the context document required "an explicit Vite build entry" for new pages and stated the page count in six places; `docs/CHANGELOG.md:48-51` (each recent page recorded as the "seventh", "eighth" and "ninth explicit Vite MPA entry"); page-count wording at `README.md:7`, `:93`, `:103`, `:139`, `:225` and `:235`; commits `0676891`, `5f3a40f` and `bcd21e0` each edited `vite.config.js`, `README.md` and the context document for one new page, and `9dd074c` rewrote all route entries in `vite.config.js`.
- **Planned improvement:** Derive the Vite MPA inputs from root-level `*.html` files (non-recursive), using Node's file-system API or the existing `fast-glob` devDependency. Replace hard-coded page counts in README (PL and EN), including the architecture sentence on Vite entry points, with count-independent wording that describes the derived-entry rule, and keep the explicit page list only in the README structure trees. The 2026-10-06 proposal applied the same wording change to the context document and kept its project-identity page list; after that document was removed on 2026-10-07, the documentation scope was limited to README. Keep `appType: "mpa"`, `base: "./"`, root-level pages, English filenames and the current `dist/` output paths. No new dependency, Vite plugin or directory restructuring. Because the change alters a documented build convention, it was to be assessed against the changelog's build-behavior criterion.
- **Expected value:** Adding or renaming a page no longer requires a separate build-configuration edit, and a page cannot silently drop out of the production build. Documentation edits for a new page are limited to the inventory lists and page-specific content.
- **Acceptance criteria:** `vite.config.js` contains no hand-maintained page list. `npm run build` emits the same nine HTML files at the same `dist/` paths as before. A temporary root-level test page is built without editing `vite.config.js`, then removed. HTML files outside the root (for example under `node_modules/` or `dist/`) are not picked up. README (PL and EN) contains no hard-coded total page count and describes the derived-entry rule.
- **Impact:** Medium
- **Effort:** Small
- **Implemented result:** `vite.config.js` builds `rollupOptions.input` with Node's native `readdirSync` on the project root: it keeps regular files (`entry.isFile()`) whose names end in `.html`, sorts them by name and keys each entry by its basename, which matches the former hand-written entry names. `appType: "mpa"` and `base: "./"` are unchanged, and `fast-glob` was not used. In README (PL and EN), the build script description, the production-build section and the architecture paragraph refer to all root-level HTML pages, describe the derived-entry rule, state that adding or renaming a page does not require editing `vite.config.js`, and contain no total page count. A Build and Tooling entry in `docs/CHANGELOG.md` records the changed build behavior; the earlier "seventh", "eighth" and "ninth explicit Vite MPA entry" entries remain as history.
- **Verification:** At completion, the production build output was byte-identical to the pre-change baseline. A temporary root-level page was built automatically without editing `vite.config.js`, and a temporary nested HTML file was not picked up; both probes were removed.
- **Known limitations:** Every regular `*.html` file in the root becomes a production entry, including a draft or temporary file left there. The README structure trees and the header, navigation and footer markup repeated in each page are still updated by hand when a page is added.

### IMP-WORKFLOW-05 — Give the Prettier workflow a defined scope and a read-only check

- **Status:** Completed without a baseline format (commit `a31c539`)
- **Affected workflow:** Code formatting and its place in the verification workflow.
- **Original state:** Formatting was available only as a repository-wide write with default options. There was no check mode or ignore file, so conformance could not be reported without modifying files. The write scope included `LICENSE.md`, the legal pages, the changelog and archived improvement records, and static inspection suggested that a run would also rewrite files unrelated to the current change. The command was therefore outside the documented verification workflow.
- **Original evidence:** `package.json:12` (`"format": "prettier --write ."`); no `.prettierrc*`, `.prettierignore` or `prettier` key in the repository; `package-lock.json:2577-2578` (Prettier 3.9.9); the context document's verification guidance (lint, build and manual checks, with no formatting step; `format` "writes across the repository and is not a read-only verification command"). Static indications that the tracked sources were not in Prettier 3 default output: `.eslintrc.cjs:4` and `.eslintrc.cjs:9` (multi-line object members without trailing commas), and `js/main.js:27-30` (multi-line call arguments without the trailing comma that the Prettier 3 default `trailingComma: "all"` adds).
- **Planned improvement:** Define the formatting scope with a `.prettierignore`, with the final list decided by the owner (for example the license text and archived records). Add a non-writing check script (for example `format:check`, running Prettier's check mode) next to the existing `format`, and update the README script tables and testing and validation sections (PL and EN) to match. Use the installed Prettier 3 defaults, with no new dependency, Prettier plugin, editor configuration, Git hook or CI job. Decide explicitly between a one-time baseline format of the in-scope files in a dedicated formatting-only commit, followed by `npm run lint`, `npm run build` and a spot check of the legal pages, and a narrower scope limited to files that already conform.
- **Expected value:** Formatting conformance can be checked without changing files. `npm run format` no longer rewrites documents that should stay byte-stable. After a baseline, formatting diffs stay confined to the files a task actually touches.
- **Acceptance criteria:** The check script exits without writing any file and reports the current conformance. Files listed in `.prettierignore` are unchanged after `npm run format`. Both README languages list the check command and describe `format` as its writing counterpart. If a baseline was applied, the check passes on a clean checkout and lint and build still succeed.
- **Impact:** Medium
- **Effort:** Medium
- **Implemented result:** `.prettierignore` excludes `/dist/`, `node_modules/`, `package-lock.json`, `/LICENSE.md`, the legal pages `/terms.html`, `/privacy.html` and `/cookies.html`, and `/docs/archive/`. `package.json` adds `"format:check": "prettier --check ."` next to the unchanged `format` script; both use the same ignore files and the unchanged Prettier 3 defaults, and the repository has no Prettier configuration. README (PL and EN) lists both commands, describes `format:check` as read-only and `format` as its writing counterpart, and states the exclusions, the absence of a baseline format and Prettier's LF expectation. No baseline format was applied, and the scope was not narrowed to files that already conform, so the check reports the existing differences. A Build and Tooling entry in `docs/CHANGELOG.md` records the change.
- **Verification:** At completion, `npm run format:check` was run and exited with code 1. On the CRLF working copy used at that time (`core.autocrlf=true`), it reported all 29 in-scope files because Prettier expects LF; an LF-normalized scratch copy reported content differences in 12 files. SHA-256 checksums and `git status` confirmed that the check changed no file, and `prettier --file-info` and `--list-different` confirmed the exclusions. `npm run format` was not run.
- **Known limitations:** Full Prettier conformance is not established: `npm run format:check` will not pass until a separately approved baseline format resolves the reported differences. The criterion that excluded files stay unchanged after `npm run format` was assessed through `prettier --file-info` and `--list-different`, not by running the writing command. Commit `d037830`, a later change outside this item, added a `.gitattributes` that checks text files out with LF line endings; the check was not re-run afterward, so the 29-file result describes the CRLF working copy verified at completion.

## Selection summary

The five proposals were selected because each one addressed a workflow that already existed in the repository but was undocumented, implicit or maintained by hand in several places. Each proposal also stayed within the current stack. Together they addressed report maintenance (01), documentation ownership, originally release recording (02), environment setup (03), page addition (04) and formatting within verification (05). Four proposals were assessed as Small and one as Medium, and none added a dependency, CI or deployment automation.

All five are closed. IMP-WORKFLOW-01 was implemented and later superseded by the simplified documentation model. IMP-WORKFLOW-02 was resolved through that model instead of its original proposal. IMP-WORKFLOW-03 and IMP-WORKFLOW-04 were implemented as planned. IMP-WORKFLOW-05 was implemented without a baseline format, so its check still reports existing formatting differences.

Order and dependencies: the items were implemented in numerical order between 2026-10-06 and 2026-10-08, with IMP-WORKFLOW-01 first, as the original dependency plan recommended. The planned interaction between IMP-WORKFLOW-02's changelog release headings and the changelog heading-structure observation lapsed when the release proposal was not adopted; the heading defect was corrected under IMP-WORKFLOW-02 instead. IMP-WORKFLOW-03 and IMP-WORKFLOW-05 both edited `package.json` and README and were delivered in separate commits.

Considered but not selected (as assessed on 2026-10-06; line references point to `200ef33`). None of these was addressed during the cycle:

- `npm run dev` exposes the development server to the local network (`package.json:9`). The behavior was documented in README and may be intentional for device testing, so it is a security-setting decision rather than a workflow gap.
- The ownership of converted images in `assets/images/` was undecided: converted output was neither tracked nor ignored by `.gitignore`. The issue stays latent while `assets/src-images/` contains no raster sources.
- The header and footer markup is repeated in every root HTML page. This is a source-organization question for a technical review, not a workflow change.
- `npm run lint` excludes the Node tooling files `scripts/convert-images.js` and `vite.config.js`. These are two small files, so extending the lint scope had lower practical value than the selected items.
