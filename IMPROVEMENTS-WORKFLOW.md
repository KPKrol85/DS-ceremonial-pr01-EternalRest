# Eternal Rest — Workflow Improvements

**Analysis date:** 2026-10-06
**Project type:** Polish-language static multi-page website (nine root HTML pages, plain CSS with custom properties, Vanilla JavaScript ES module, Vite 5 MPA build, npm tooling)
**Analysis mode:** Evidence-based workflow improvement review
**Focus:** Project-wide workflow

## Improvement overview

The development workflow is small and mostly well documented. Six npm scripts in `package.json` cover development, build, preview, lint, formatting and image conversion. `vite.config.js` is the only build configuration, and `dist/` is generated and ignored. `AGENTS.md` (imported by `CLAUDE.md`) holds the shared contributor contract, `docs/CONTEXT-PROJECT.md` holds stable technical contracts, and `docs/CHANGELOG.md` has an explicit entry policy. Improvement reports have an archive directory and one completed UI cycle.

The gaps are in the steps around that core. Some workflows are referenced but not written down: manual deployment and the improvement-report status format. Some requirements are only implicit: the supported Node.js version. Some facts are maintained by hand in several places: the page inventory, which is kept in `vite.config.js` and in page-count wording across README and CONTEXT. The formatting command can only rewrite the whole repository. The five proposals below address these gaps within the current stack, the manual deployment model and the existing documentation ownership.

## Proposed improvements

### IMP-WORKFLOW-01 — Define the improvement-report lifecycle in the project contract

- **Status:** Completed — `AGENTS.md` defines one working-document lifecycle: active plans, audits and improvement reports at the repository root, category-based archives and a single verified completion status per item, with commit references optional. Static review confirmed the rule is unique and adds no Git or execution-workflow requirement; no lint, build or browser check was run because application behavior is unchanged.
- **Affected workflow:** Improvement-report maintenance: recording item completion during implementation and archiving a completed report.
- **Evidence:** `AGENTS.md:20` (names only the archive directory `docs/archive/improvements/`); `AGENTS.md:100` ("Use the project's established concise completion format"; no repository file defines that format); `docs/CHANGELOG.md:24` (status updates and archiving are not changelog entries); the pre-archive report (`git show 200ef33^:IMPROVEMENTS-UI.md`, lines 18 and 28) gave IMP-UI-01 two `**Status:**` lines in different forms (`Completed — …` and `Implemented. …`); commit `7d10c0a` ("Standardize improvement status and changelog policy") changed the status wording during the cycle; `docs/archive/improvements/IMPROVEMENTS-UI-2026-10-06.md:1-24` and commit `200ef33` show that archiving rewrote the whole report with new header fields, a "How to read this record" section and renamed item fields (Original state, Original evidence, Planned improvement, Implemented result, Verification, Known limitations).
- **Current workflow:** The repository records only where completed reviews go. The status-line format, the point at which a report is archived, the archive filename pattern (the single example is `IMPROVEMENTS-UI-<YYYY-MM-DD>.md`) and the structure of an archived record are inferred from one completed cycle. During that cycle the status format changed once and one item ended up with two status lines. Archiving then required restructuring the full report. This report is the second to enter the same lifecycle.
- **Proposed improvement:** Add a short improvement-report lifecycle rule next to the existing rules in `AGENTS.md`. It should cover: the active report location and name (`IMPROVEMENTS-<AREA>.md` in the root), one per-item status format (outcome, commit reference, checks actually run), when a report is archived, the archive filename pattern, and the minimum archived-record fields. The existing UI archive serves as the reference example, so no new template file is needed. If the status format comes from a global KP_Code standard kept outside the repository, the local rule should reference that standard and record only project-specific choices (paths, naming, archive fields). Refining the global standard is a separate change.
- **Expected practical value:** Each new cycle records completion in one form from the first completed item. Archiving needs less restructuring because the archived fields are defined in advance. The instruction at `AGENTS.md:100` points to a format that can actually be found.
- **Implementation scope:** One short addition to `AGENTS.md`, consolidating lines 20 and 100 where needed. `CLAUDE.md` stays import-only, and the rule is not repeated in README or CONTEXT. No change to the archived UI report, the changelog entry policy, scripts or tooling, and no new template file.
- **Acceptance criteria:** `AGENTS.md` states the active report location and naming, a single status-line format that includes the commit and the verification actually run, the archive trigger, and an archive filename pattern that matches `docs/archive/improvements/IMPROVEMENTS-UI-2026-10-06.md`. The completion format referenced at `AGENTS.md:100` is defined, or explicitly referenced, in the repository. The rule exists in exactly one project file.
- **Impact:** Medium
- **Effort:** Small

### IMP-WORKFLOW-02 — Document the manual release procedure and make the deployed revision traceable

- **Affected workflow:** Deployment preparation and release recording.
- **Evidence:** `AGENTS.md:61` (contributors must follow "the project's manual deployment workflow"); `docs/CONTEXT-PROJECT.md:98-100` (`dist/` is the static-hosting artifact; no hosting configuration, deployment command or CI deployment workflow); `README.md:11-13` and `README.md:143-145` (preview URL whose correspondence with the repository revision "has not been confirmed"); `README.md:105` and `README.md:237`; `docs/CHANGELOG.md:7` (every entry sits under `[Unreleased]`); `package.json:3` (`"version": "1.0.0"`); the repository has no Git tags.
- **Current workflow:** The repository defines the artifact (`npm run build` → `dist/`) and a local inspection command (`npm run preview`). `AGENTS.md` refers to a manual deployment workflow that no file describes: there are no pre-publish checks, no documented route for `dist/` to reach the host, and no record of which revision was published. Every change since the first commit remains under `[Unreleased]`, the package version has not changed, and there are no tags. As a result, the repository cannot identify the live revision, and README has to disclaim the preview URL.
- **Proposed improvement:** Add one short manual release procedure to `docs/CONTEXT-PROJECT.md` under its existing "Deployment" section. The procedure covers: clean install (`npm ci`), `npm run lint`, `npm run build`, a local check with `npm run preview`, the owner's actual method of publishing `dist/`, and a recording step that ties the published commit to a dated changelog release heading, optionally with an owner-created Git tag. It also states whether `package.json` `version` follows release headings or stays fixed. README links to the procedure instead of restating it.
- **Expected practical value:** The instruction at `AGENTS.md:61` gets a concrete referent. A clean-install build before each publish lowers the risk of publishing a stale or locally modified `dist/`. The live demo can be related to a specific commit and changelog section, so README's disclaimer can be narrowed once a release has been recorded.
- **Implementation scope:** Documentation only: one procedure section in `docs/CONTEXT-PROJECT.md`, a one-line pointer in each README language, and a release-heading convention in `docs/CHANGELOG.md`. The owner must supply the publishing method, because it cannot be determined from the repository. No hosting configuration, CI workflow, deployment script or version-bump tooling is added. Tagging, deploying and version changes remain owner-initiated actions, as `AGENTS.md:61` requires.
- **Acceptance criteria:** One file owns the release procedure, and both README languages link to it without repeating its steps. The procedure references only commands defined in `package.json`, plus the owner-confirmed publishing step. It states how a published revision is recorded (release-heading format with date and, if used, tag name) and the role of `package.json` `version`. `AGENTS.md:61` refers to a workflow that exists in the repository. No deployment, CI or hosting file is added.
- **Impact:** High
- **Effort:** Small

### IMP-WORKFLOW-03 — Declare the supported Node.js and npm versions

- **Affected workflow:** Development setup and reproducible dependency installation.
- **Evidence:** `package.json:1-25` (no `engines` field); the root has no `.nvmrc`, `.node-version` or `.npmrc`; `README.md:80` and `README.md:212` ("Node.js and npm are required", without versions); `docs/CONTEXT-PROJECT.md:18`; locked dependency constraints: `package-lock.json:2758` (sharp 0.33.5, Node `^18.17.0 || ^20.3.0 || >=21.0.0`), `package-lock.json:2977` (vite 5.4.21, Node `^18.0.0 || >=20.0.0`), `package-lock.json:2675-2676` (rollup 4.64.0, Node `>=18.0.0`, npm `>=8.0.0`); `package-lock.json:918` (`@napi-rs/lzma-linux-x64-gnu` 1.5.1, an optional Linux x64 dependency of rollup, Node `^22.20 || ^24.12 || >=25`); `package-lock.json:4` (`lockfileVersion: 3`).
- **Current workflow:** The setup instructions require Node.js, npm and `npm ci`, but the supported runtime exists only in the engine ranges of locked third-party packages. The required dependencies set a floor of Node `^18.17.0 || ^20.3.0 || >=21.0.0` and npm `>=8`. On Linux x64, one optional rollup dependency requires Node `^22.20 || ^24.12 || >=25`. Both constraints can only be found by reading the lockfile, and the second one depends on the platform. npm does not enforce engine ranges by default, so an unsuitable runtime shows up only as engine warnings for individual packages or as a later tool failure.
- **Proposed improvement:** Record the supported Node.js and npm range once, in `package.json` `engines`. Choose a range that falls within the locked dependency constraints, accounts for the optional platform-specific constraint above, and includes the version the owner actually uses. Both README installation sections reference that range.
- **Expected practical value:** A fresh clone states its expected runtime before `npm ci`. Mismatches are reported against the project's own declaration, not only against transitive packages. The README requirement becomes specific and verifiable.
- **Implementation scope:** `engines` in `package.json`, the matching root-package entry in `package-lock.json` updated through npm's own tooling with no change to resolved dependency versions, the two README installation paragraphs, and `docs/CONTEXT-PROJECT.md:18` if it names the requirement. No dependency upgrades, no `engine-strict` enforcement and no required version-manager file.
- **Acceptance criteria:** `package.json` declares an `engines` range that falls within the required-dependency constraints above. The range either falls within the optional Linux x64 constraint or the documentation explains why it does not. README (PL and EN) states the same range. `npm ci` on a Node.js version inside the range reports no engine warnings for required packages. The diff of `package-lock.json` contains no resolved-version changes.
- **Impact:** Medium
- **Effort:** Small

### IMP-WORKFLOW-04 — Make the root HTML pages the single source of the page inventory

- **Affected workflow:** Adding, renaming or removing a page (build entries and documentation synchronization).
- **Evidence:** `vite.config.js:12-22` (nine hand-written `rollupOptions.input` entries); `docs/CONTEXT-PROJECT.md:25` and `docs/CONTEXT-PROJECT.md:64` ("New pages require an explicit Vite build entry"); `docs/CHANGELOG.md:48-51` (each recent page recorded as the "seventh", "eighth" and "ninth explicit Vite MPA entry"); page-count wording at `README.md:7`, `:93`, `:103`, `:139`, `:225`, `:235` and `docs/CONTEXT-PROJECT.md:9`, `:25`, `:64`, `:85`, `:100`, `:105`; commits `0676891`, `5f3a40f` and `bcd21e0` each edited `vite.config.js`, `README.md` and `docs/CONTEXT-PROJECT.md` for one new page, and `9dd074c` rewrote all route entries in `vite.config.js`.
- **Current workflow:** Each new page must be registered by hand in `vite.config.js`, and the total page count is repeated in twelve documentation sentences across README (both languages) and CONTEXT. Vite builds only the listed inputs, so a page that is not registered is left out of `dist/` and the build does not report the omission.
- **Proposed improvement:** Derive the Vite MPA inputs from root-level `*.html` files (non-recursive), using Node's file-system API or the existing `fast-glob` devDependency. Replace hard-coded page counts in README and CONTEXT with count-independent wording. Keep the explicit page list only where it serves as the inventory: the CONTEXT project identity and the structure trees.
- **Expected practical value:** Adding or renaming a page no longer requires a separate build-configuration edit, and a page cannot silently drop out of the production build. Documentation edits for a new page are limited to the inventory lists and page-specific content.
- **Implementation scope:** Input construction in `vite.config.js`; count wording in README (PL and EN) and CONTEXT; `docs/CONTEXT-PROJECT.md:25` and `:64` updated to describe the derived-entry rule. Keep `appType: "mpa"`, `base: "./"`, root-level pages, English filenames and the current `dist/` output paths. No new dependency, Vite plugin or directory restructuring. This changes a documented build convention, so the implementing task should be assessed against the changelog's build-behavior criterion.
- **Acceptance criteria:** `vite.config.js` contains no hand-maintained page list. `npm run build` emits the same nine HTML files at the same `dist/` paths as before. A temporary root-level test page is built without editing `vite.config.js`, then removed. HTML files outside the root (for example under `node_modules/` or `dist/`) are not picked up. README and CONTEXT contain no hard-coded total page count. CONTEXT describes the derived-entry rule.
- **Impact:** Medium
- **Effort:** Small

### IMP-WORKFLOW-05 — Give the Prettier workflow a defined scope and a read-only check

- **Affected workflow:** Code formatting and its place in the verification workflow.
- **Evidence:** `package.json:12` (`"format": "prettier --write ."`); no `.prettierrc*`, `.prettierignore` or `prettier` key in the repository; `package-lock.json:2577-2578` (Prettier 3.9.9); `docs/CONTEXT-PROJECT.md:94` (verification guidance covers lint, build and manual checks, with no formatting step); `docs/CONTEXT-PROJECT.md:96` (`format` "writes across the repository and is not a read-only verification command"). Static indications that the tracked sources are not in Prettier 3 default output: `.eslintrc.cjs:4` and `.eslintrc.cjs:9` (multi-line object members without trailing commas), and `js/main.js:27-30` (multi-line call arguments without the trailing comma that the Prettier 3 default `trailingComma: "all"` adds).
- **Current workflow:** Formatting is available only as a repository-wide write with default options. There is no check mode or ignore file, so conformance cannot be reported without modifying files. The write scope includes `LICENSE.md`, the legal pages, the changelog and archived improvement records. Static inspection suggests that a run would also rewrite files unrelated to the current change. The command is therefore outside the documented verification workflow and conflicts with the focused, one-change-per-commit practice in `AGENTS.md`.
- **Proposed improvement:** Define the formatting scope with a `.prettierignore`; the owner decides the final list, for example the license text and archived records. Add a non-writing check script (for example `format:check`, running Prettier's check mode) next to the existing `format`. Also decide explicitly between a one-time baseline format of the in-scope files in a dedicated commit and a narrower scope limited to files that already conform.
- **Expected practical value:** Formatting conformance can be checked without changing files. `npm run format` no longer rewrites documents that should stay byte-stable. After a baseline, formatting diffs stay confined to the files a task actually touches.
- **Implementation scope:** `.prettierignore`, one script in `package.json`, and matching updates to the verification guidance in `docs/CONTEXT-PROJECT.md` and the README script tables. Use the installed Prettier 3 defaults. No new dependency, Prettier plugin, editor configuration, Git hook or CI job. If a baseline format is chosen, it is a formatting-only commit followed by `npm run lint`, `npm run build` and a spot check of the legal pages for unintended rendering changes.
- **Acceptance criteria:** The check script exits without writing any file and reports the current conformance. Files listed in `.prettierignore` are unchanged after `npm run format`. README and CONTEXT list the check command and describe `format` as its writing counterpart. If a baseline was applied, the check passes on a clean checkout and lint and build still succeed.
- **Impact:** Medium
- **Effort:** Medium

## Selection summary

The five proposals were selected because each one addresses a workflow that already exists in the repository but is undocumented, implicit or maintained by hand in several places. Each proposal also stays within the current stack, the manual deployment model and the existing ownership of `AGENTS.md`, CONTEXT, README and the changelog. Together they strengthen report maintenance (01), release preparation (02), environment setup (03), page addition (04) and formatting within verification (05).

- **Dependencies:** IMP-WORKFLOW-01 is best implemented first, so that the completion of the remaining items is recorded in the agreed format. IMP-WORKFLOW-02 introduces changelog release headings, which interact with the heading-structure observation below. IMP-WORKFLOW-03 and IMP-WORKFLOW-05 both edit `package.json` and README, so implementing them in separate commits keeps each change reviewable.
- **Independence:** IMP-WORKFLOW-03, -04 and -05 can be implemented in any order. IMP-WORKFLOW-02 needs the owner's publishing method before it can be written.
- **Scope:** Four proposals are Small and one is Medium. None adds a dependency, CI or deployment automation. Together they form a practical candidate backlog for a focused working session, without a guaranteed completion time.

Considered but not selected:

- `npm run dev` exposes the development server to the local network (`package.json:9`). The behavior is documented in README and CONTEXT and may be intentional for device testing, so it is a security-setting decision rather than a workflow gap.
- The ownership of converted images in `assets/images/` is undecided (`docs/CONTEXT-PROJECT.md:88`). The issue stays latent while `assets/src-images/` contains no raster sources.
- The header and footer markup is repeated across all pages (`docs/CONTEXT-PROJECT.md:64`). This is a source-organization question for a technical review, not a workflow change.
- `npm run lint` excludes the Node tooling files `scripts/convert-images.js` and `vite.config.js`. These are two small files, so extending the lint scope has lower practical value than the selected items.

## Excluded observations

The following documentation inaccuracies were observed during the analysis. They are defects, not optional improvements, so they were not presented as proposals and were not corrected.

- `docs/CHANGELOG.md:7-57`: `## Entry policy` (line 9) sits between `## [Unreleased]` (line 7) and its `### Added`, `### Build and Tooling` and `### Documentation` subsections (lines 28, 46 and 57). In the heading hierarchy, all unreleased entries therefore belong to "Entry policy". This is relevant to IMP-WORKFLOW-02.
- `.gitignore:107-128`: the "Intentionally tracked" comment lists root `PLAN.md`, `CHANGELOG.md` and `CONTEXT-PROJECT.md`. Two of these now live in `docs/`, and no `PLAN.md` exists. The comment also lists `site.webmanifest`, `service-worker.js`, `service-worker-bundles.json`, `_headers` and `_redirects`, none of which exist. `docs/CONTEXT-PROJECT.md:109` already warns that the comment does not establish their existence.
- The project-structure trees omit current files. `README.md:41-76` and `README.md:173-208` omit `docs/`, `AGENTS.md` and `CLAUDE.md`, and `docs/CONTEXT-PROJECT.md:41-57` omits `AGENTS.md`, `CLAUDE.md`, `docs/CONTEXT-PROJECT.md` and `docs/archive/`.

## Analysis limitations

- `node_modules/` is not installed, and installation was outside the scope of this analysis, so no npm command (lint, build, preview or a Prettier check) was executed. The formatting state described in IMP-WORKFLOW-05 is inferred from static inspection.
- The hosting account, the publishing method and the live preview were not inspected. IMP-WORKFLOW-02 depends on the owner to supply the actual publishing step.
- The owner's local Node.js and npm versions are unknown. The versions in the analysis environment (Node.js 22.22.0, npm 10.9.4) are not evidence of the project's supported range.
- No `PLAN.md`, audit, review or other active improvement report exists. Overlap with planned or completed work was checked against `AGENTS.md`, `README.md`, `docs/CONTEXT-PROJECT.md`, `docs/CHANGELOG.md`, the archived UI report and Git history up to commit `200ef33`.
